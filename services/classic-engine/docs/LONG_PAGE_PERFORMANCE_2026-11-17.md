# 长图性能与优化方向

## 测试范围

2026-11-17，Apple M6 Mac mini，12 核 CPU / 12 核 GPU、24 GB 统一内存，PyTorch 2.14.1。样本 `5d2fe9e0-7cb2-4c72-94ba-967025a3eb2a.jpg`，930×28007，26,046,510 像素，JPEG 1,177,006 字节。

原配置：MPS、Hayai FP16、LaMa FP32、检测批量 1、OCR 批量 8、计算页槽 2、CPU 线程 2、渲染进程 2、页面预算 2 GiB。测试前排空并暂停本地节点，使用同一套真实模型和字体；生产配置不变。

单页测试用固定中文测试句子嵌字；连续任务复用项目的真实 `Agent` / `Pipeline` / `Journal`，中心、译文和传输为本地模拟，使用工具自带英文测试句子。两类渲染耗时不可直接当作同一种译文对照。图片、识别全文及私有结果不入仓库。

## 优化前单页结果

预热后两轮平均：

| 阶段 | 秒 | 主要工作 |
| --- | ---: | --- |
| JPEG 校验、解码 | 0.047 | CPU |
| 分析 | 9.56 | 检测、OCR、颜色、气泡、掩膜、检查点 |
| 其中：文字检测 | 7.57 | 38 次 DBNet 前向 |
| 其中：纯 OCR | 约 0.63 | 4 批 Hayai，31 个候选段落 |
| 抹字 | 2.56 | 14 个纯色填充匹配区域，16 次 LaMa |
| 中文嵌字、差分与无损输出 | 1.43 | CPU 排版约 0.49 秒，输出约 0.91 秒 |
| 单独测量结果冻结 | 0.028 | SQLite 持久事务 |

本地串行合计约 **13.6 秒**，不含真实中心翻译、下载和上传。保留 30 个识别区域，未截断；输出为 7 个 WebP 覆盖块，943,144 字节。

分析与抹字阶段整机 GPU 活跃度均约 85%–86%；平均 CPU 消耗分别约 0.40、0.42 核。连续单独渲染时 GPU 活跃度为 0，CPU（含子进程）约 1.25–1.31 核。GPU 活跃度不是理论 FLOPS 或进程独占 GPU 时间；CPU 低占用不等于资源浪费。

当前配置重复执行的分析、抹字和输出摘要一致。分析/渲染调参除特别注明外也保持结果摘要一致。

## 优化前已验证的取舍

### 线程和检测批量

| 设置 | 分析秒/页，两轮平均 | MPS 驱动分配观察值 |
| --- | ---: | ---: |
| 原配置，起始对照 | 9.56 | 2.83 GiB |
| CPU 线程 2 → 4 | 9.57 | 2.83 GiB |
| 检测批量 1 → 2 | 9.71 | 3.94 GiB |
| 检测批量 1 → 4 | 9.28 | 5.14 GiB |
| 恢复原配置，末尾对照 | 9.22 | 4.84 GiB |

首尾运行状态有漂移，不能把批量 4 相对起始对照的全部差值认作优化收益。批量增大将 38 次前向减到 19/10 次，但没有显示明确提速，驱动分配明显增加；恢复批量 1 后分配仍保留部分缓存。本例不建议提高批量或每页清空 GPU 缓存。

### 并发、首张延迟与吞吐

同一长图作为 4 个独立任务，经真实本地调度、内存门控、进程 IPC、冻结及模拟交付；每组一轮：

| 设置 | 4 张完成总耗时 | 首张开始交付 | 整机 GPU 平均 |
| --- | ---: | ---: | ---: |
| 当前：计算槽 2、抹字槽 2 | 48.24 秒 | 22.69 秒 | 85.8% |
| 计算槽 1、抹字槽 1 | 49.52 秒 | 13.85 秒 | 83.1% |
| 计算槽 2、抹字槽 1 | 48.51 秒 | 22.86 秒 | 85.0% |

单计算槽首张约提前 39%，整批约慢 2.6%；单次实验不足以确定微小吞吐差异。现有两个计算任务争用同一把 MPS 全局锁，先提交的长分析会挡住已准备好的抹字。仅限制抹字槽没有解决首张延迟。

全部 12 个任务正确完成、输出摘要一致、临时日志清空，预留量均不超过 2 GiB。当前配置可同时准备约 3 张这样的图；渲染缓存预算前两张只有一张整页掩膜，后两张才有完整缓存。测试的整批 CPU 平均约 0.62–0.63 核，渲染已经与下一张 GPU 工作重叠。

### 参考掩膜缓存

固定中文输出，其他条件相同：

| 可选缓存预算 | 实际保留参考掩膜 | 重建次数 | 渲染总耗时 |
| --- | ---: | ---: | ---: |
| 0 | 0 | 59 | 1.438 秒 |
| 64 MiB | 49.7 MiB | 50 | 1.422 秒 |
| 256 MiB | 248.4 MiB | 32 | 1.423 秒 |

输出字节完全一致。大缓存相对无缓存约快 1%，此样本收益偏低。这里的预算/逻辑数组大小不能等同于物理内存驻留：全零页及共享映射可能重复或延迟计费。

一张 uint8 全页掩膜约 24.84 MiB，int32 连通标签约 99.36 MiB。当前参考掩膜按整页形状缓存，16 组组合请求约 397.4 MiB；渲染 IPC 另需约 298.1 MiB。单页独占大缓存会挤压其他页和 IPC 的准入空间。

进程池渲染约 1.42 秒，同页退回本进程约 1.76 秒；后者输出编码只有一个工作线程。不能为了消除 IPC 便直接取消进程池。

### 无损输出编码

复用原配置生成的中文最终像素，单独比较 `pack_result` 的差分、WebP 编码、校验和封包；不包含排版及 GPU 计算。每组 3 轮，method 4 / 2 线程在首尾各测 3 轮：

| WebP method / 工作线程 | 耗时 | CPU 时间 | 输出字节 |
| --- | ---: | ---: | ---: |
| 4 / 2（原编码设置） | 0.9091 秒 | 1.1667 秒 | 943,087 |
| 4 / 4 | 0.4826 秒 | 1.2140 秒 | 943,087 |
| 1 / 2 | 0.8459 秒 | 1.0850 秒 | 966,311 |
| 2 / 2 | 0.8734 秒 | 1.1307 秒 | 950,097 |
| 0 / 2 | 0.3055 秒 | 0.4276 秒 | 5,263,109 |
| 0 / 4 | 0.1687 秒 | 0.4593 秒 | 5,263,109 |

所有输出重建像素与基准完全一致。method 4 从 2 增至 4 线程，输出耗时约降低 47%，累计 CPU 时间约增加 4%，文件大小相同；这是单页编码延迟收益，尚未证明整批吞吐或耗电改善。应复用渲染池现有空闲线程借用预算，避免多个页面同时扩大线程数。

method 0 减少 CPU 工作量，但文件膨胀到约 5.58 倍，增加约 4.32 MB/页的传输及存储。method 1/2 的小幅提速也伴随体积增加；本例优先保留 method 4、研究有界并行。实验清单使用固定占位输入摘要，因此 943,087 字节与完整单页的 943,144 字节略有不同，应在各自实验内比较。

### 减少检测补边

当前 930×930 切片补成 1280×1280，约 47.2% 输入面积为补边。实验保持原图分辨率、38 个切片、930 的切片边长和 732 的纵向步长不变，只改变模型输入边长：

| 输入边长 | 分析耗时 | 累计模型输入像素 | 输出对照 |
| --- | ---: | ---: | --- |
| 1280，前置对照两轮 | 9.494 / 9.605 秒 | 62,259,200 | 与基准一致 |
| 1024，两轮 | 6.923 / 6.943 秒 | 39,845,888 | 文字、区域、掩膜不同 |
| 1280，后置对照两轮 | 9.820 / 9.706 秒 | 62,259,200 | 与基准一致 |

1024 减少 36% 输入像素，分析相对前后对照均值约快 28%。区域数仍为 30，但文字与区域内容不同；修复掩膜差 2,092 像素、原始掩膜差 72,301 像素，气泡掩膜相同。抹字结果差 235,987 像素，最大通道差 213。尚未人工判定这些变化的优劣，不能作为结果等价的优化直接替换。

960 输入在预热时出现特征图拼接尺寸不匹配（`DBNet_resnet34.py:118`，预期 6、实际 7），测试守护已恢复节点。该模型下采样到 1/256，不能仅按通常的 32 像素对齐；即使尺寸兼容，补边变化也会影响模型预测。

## 研究确定的优化顺序

1. **按 MPS 实际串行能力调度。** 优先推进已完成分析的抹字，避免另一个长分析提前占住 GPU；单计算槽可作为长图首张延迟的对照基线。纯 CPU 的分组、裁剪、掩膜细化可以研究移到设备锁外，所有 GPU 操作、传输和模型卸载仍需互斥保护。该调度改动尚未实测，不能把单槽收益直接当作其收益。
2. **限制低收益的整页参考掩膜缓存。** 先用较小预算或按需重建降低页面预留，再研究复用连通块 bounds，以 ROI 加坐标原点表示参考掩膜。此样本中 64 MiB 与 256 MiB 预算耗时相当，逻辑保留量相差约 199 MiB；ROI 改动还需覆盖排版、碰撞和坐标还原。
3. **把空闲 CPU 预算用于输出块并行。** 保留 method 4、复用现有线程预算借用机制，以本次 2/4 线程对照为依据，验证 GPU 与多页渲染混合负载下的收益。4 线程省约 0.43 秒/页的输出阶段等待；不据此承诺同等整批提速。
4. **在长计算的安全边界响应取消。** 当前分析/抹字入口没有接收页面取消回调，取消检查主要在阶段前后；长图已经取消时可能仍做完整段计算。适合在检测切片、OCR 批次、LaMa 块之间检查，停止提交后续工作，已提交设备操作排空后再释放缓冲区。取消响应改善尚待真实模型测试。
5. **修正 macOS CPU 自动预算识别。** 当前 affinity API 不可用就保守回退一核，造成诊断及 `auto` 预算失真。显式 2 线程仍生效。应区分平台“不支持接口”和“读取受限”，保持 Linux cgroup、Windows affinity 的现有边界；修正容量识别不等于直接启用全部核心。
6. **将检测补边作为需要质量回归的算法实验。** 1024 的约 28% 分析提速值得继续研究，但文字与抹字已经变化。先覆盖小字、切片接缝和气泡边缘的标注对照，再决定是否采用；960 的形状错误也说明需要模型级尺寸约束。

## 实施

- MPS 在普通图片、文档共享调度器中只派发一个分析／抹字任务，下一项仍按准备状态和文档等待时间选择；渲染与网络保持独立并发。设备互斥继续覆盖传输与模型操作。
- 参考掩膜请求按每页 64 MiB 向下取整为完整掩膜，实际预留仍受总页面预算限制。本图最多保留两张整页参考掩膜，约 49.7 MiB；连通标签和 IPC 的预算独立。
- macOS 缺少 affinity API 时使用已知逻辑核心数；未知核心数仍回退一核。本机原配置解析为 12 核容量、每个渲染进程 4 线程、渲染池共 8 核预算。沿用现有非阻塞额度借用机制，单页编码最多使用空闲池预算和实际块数中的较小值。
- 普通图片和文档阶段通过 `ContextVar` 携带租约取消检查器，`asyncio` 模型调用继承该上下文，退出阶段时复位。检测用 PyTorch 前向前钩子，Hayai／Paddle／日文 OCR、取色及 LaMa 在批次或块边界检查；不修改模型输入、权重和上游资产。

相关调度、预算、OCR、渲染进程及恢复回归共 669 项通过；子进程退出测试补齐临时测试依赖路径后通过。测试依赖安装在本机临时目录。

提交前合并 LaMa 的锁与取消测试，把 MPS 覆盖并入已有并发／公平调度用例，删除仅验证 PyTorch 钩子机制的重复测试，并移除阶段入口的重复取消检查；整理后 672 项回归通过。

24 个调度任务全部完成且交付日志清空。原包／新代码的分析内容、抹字像素和中文输出字节均与前轮基准一致；四任务英文输出字节跨版本也一致。全部无新增换出，页面预留峰值均约 1.99 GiB。RSS 求和峰值分别约 6.52–6.77 / 6.76–6.82 GiB，未观察到物理驻留明显下降；减少参考缓存逻辑保留量不能直接宣称节省同等 RSS。

### 正式流式补丁与资产验证

### 正式补丁真实模型交错复测

## 已有有效措施及低优先级项

- 灰度文本跳过颜色模型：本图 20 个区域走快速路径，仅 10 个区域估色。
- 纯色气泡先 CPU 填充；LaMa 只修复剩余 16 块。逐块结果会成为后续上下文，不能随意合批。
- 热模型、OCR 批量、页面内裁剪缓存、掩膜和连通标签复用、共享内存及分块输出均已启用。
- 分析检查点约 1.84 MB，三张掩膜编码约 0.05–0.08 秒；JPEG 解码约 0.047 秒；实际流水线结果冻结约 0.005–0.009 秒。这些不是本图主瓶颈。
- profiler 的 `Tensor.cpu()` 大量时间包含等待 GPU 完成，不能解释成纯复制成本，更不能承诺去掉回传就能省掉全部时间。CPU refine 约数百毫秒，有优化空间但优先级低于检测。
- 保留输入摘要、掩膜校验、输出解码校验和持久化恢复。它们在信任边界或保证交付语义，不应当作“无效操作”删除。
